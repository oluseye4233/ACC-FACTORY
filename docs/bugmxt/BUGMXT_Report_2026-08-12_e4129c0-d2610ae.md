## Layer 1 — Syntax Sweep

- **[SYNTAX-001] | Severity: MEDIUM | File: `lib/api-zod/src/generated/api.ts` | Line: ~1710**
  **Issue:** `recentTicks` is declared as `zod.array(zod.coerce.date())`. The API server serialises `recentTicks` as `string[]` (ISO-8601 strings via `Date.prototype.toISOString()`), and the OpenAPI spec declares each item as `{ type: string, format: date-time }`. `zod.coerce.date()` will coerce those strings to `Date` objects on parse — but the generated TypeScript type in `lib/api-zod/src/generated/types/cronTargetStatus.ts` declares `recentTicks: Date[]`, while the React client interface in `lib/api-client-react/src/generated/api.schemas.ts` declares `recentTicks: string[]`. This three-way disagreement (Zod schema → `Date[]`; React client type → `string[]`; wire format → `string[]`) means the inferred type from the Zod validator is `Date[]`, but the value passed to the UI component `TickStrip` — which calls `new Date(iso)` on each element — is actually a `Date` object, making the `new Date(Date)` call silently redundant rather than crashing, but any string operation on `recentTicks` items (e.g. `indexOf`, `toISOString()`, template literals) in a consumer using the Zod-inferred type will behave unexpectedly.
  **Fix:** Align the contract at the generator config level. The correct Zod validator for a wire-format ISO date-time string that should stay a string is `zod.string().datetime()`, not `zod.coerce.date()`. Change the generated line to:
  ```diff
  - "recentTicks": zod.array(zod.coerce.date()).describe('Most recent tick timestamps (newest first), bounded window.'),
  + "recentTicks": zod.array(zod.string().datetime()).describe('Most recent tick timestamps (newest first), bounded window.'),
  ```
  Then update `lib/api-zod/src/generated/types/cronTargetStatus.ts` accordingly:
  ```diff
  - recentTicks: Date[];
  + recentTicks: string[];
  ```
  This aligns all three representations: wire (`string`), Zod schema (`string().datetime()`), TypeScript type (`string[]`).

- **[SYNTAX-002] | Severity: LOW | Files: `lib/db/migrations/0006_purple_invisible_woman.sql`, `lib/db/migrations/meta/_journal.json`**

## Layer 2 — Logic & Outcome Audit

### [LOGIC-001] | Severity: HIGH | Non-atomic insert-then-prune opens a data-loss race

Two concurrent `recordCronTick` calls for the same target both insert a row and then independently compute and execute a `DELETE ... NOT IN (SELECT TOP N)`. The second delete sees both new rows plus all pre-existing rows; whichever transaction commits last can prune the other's freshly inserted row, permanently losing a tick event. The subquery is not wrapped in the same transaction as the insert.

**File:** `artifacts/api-server/src/lib/cron-heartbeat.ts` — `recordCronTick()`, lines ~108–122

**Expected:** Both ticks survive after concurrent calls; table is bounded to `CRON_TICK_HISTORY_LIMIT`.
**Actual:** One tick can be silently deleted under concurrent load.

**Fix pathway:** Patch — wrap the insert + delete pair in a single `db.transaction(async (tx) => { … })` call.

### [LOGIC-002] | Severity: HIGH | `notInArray` with an empty subquery deletes all rows for the target

When `CRON_TICK_HISTORY_LIMIT` is zero (misconfiguration) or when the `SELECT id … LIMIT 0` subquery legally returns zero rows, Drizzle emits `NOT IN (SELECT …)` where the subquery is empty. In PostgreSQL, `NOT IN` an empty set is `TRUE` for every row, so the delete matches and removes **all** rows for the target, not just the excess.

**File:** `artifacts/api-server/src/lib/cron-heartbeat.ts` — pruning delete, lines ~115–121

**Expected:** Zero pruning when limit ≥ current row count.
**Actual:** All rows deleted if the subquery returns nothing.

**Fix pathway:** Patch — add a guard: skip the delete when `CRON_TICK_HISTORY_LIMIT` is reached or when the subquery result is empty; or use a `DELETE … WHERE id IN (SELECT id … OFFSET LIMIT)` pattern instead of `NOT IN`.

### [LOGIC-003] | Severity: MEDIUM | `ticksLast24h` over-counts when pre-existing dev rows exist in the 24h window

`getCronTargetStatuses` queries the `cron_tick_events` table for all events `> windowStart` for the target, then sets `ticksLast24h = targetEvents.length`. The test in `"caps recentTicks at 20…"` asserts `ticksLast24h >= 22`, acknowledging pre-existing rows may inflate the count — but the same inflation affects the production flakiness line. The "expected N, got M" display will appear healthy even when the schedule fired fewer times than expected, if pre-existing rows pad the count.

**File:** `artifacts/api-server/src/lib/cron-heartbeat.ts` — `getCronTargetStatuses()`, line ~234

**Expected:** `ticksLast24h` reflects only ticks recorded since this feature was deployed or within a clean window.
**Actual:** Stale dev rows (or rows from a previous run period) inflate the counter, masking a genuine shortfall.

**Fix pathway:** Patch — this is inherent to the rolling-window design; no code change is strictly required, but a `>= 22` assertion instead of `=== 22` in the test is an accepted concession. In production, the bounded prune (200 rows) is the real guard. Accept as low-risk acknowledged design trade-off, or document explicitly in the `ticksLast24h` JSDoc.

### [LOGIC-004] | Severity: MEDIUM | `expectedTicksLast24h` is zero for coarse schedules, but `TickStrip` still renders gap warnings against a zero threshold

`expectedTicksLast24h = Math.floor((24 * 60) / cfg.expectedIntervalMinutes)`. For a schedule coarser than daily (`expectedIntervalMinutes > 1440`), this is 0. `TickHistoryLine` correctly gates on `< 1`. However, `TickStrip` unconditionally renders and computes `gapThresholdMs = t.expectedIntervalMinutes * 2 * 60_000`. For the weekly-digest schedule (`expectedIntervalMinutes = 10080`), this is ~14 days — so every dot renders green and no gap warning is ever shown, which is silently wrong (the strip is meaningless). There is no guard preventing the strip from rendering with misleading confidence for coarse schedules.

**File:** `artifacts/command-centre/src/pages/admin-ops.tsx` — `TickStrip` component

**Expected:** Strip is suppressed or clearly annotated as non-applicable for schedules coarser than daily.
**Actual:** Strip renders with an outsized gap threshold that never triggers amber, giving false confidence.

**Fix pathway:** Patch — add `if (t.expectedTicksLast24h < 1) return null;` at the top of `TickStrip`, consistent with `TickHistoryLine`'s existing guard.

**Expected:** Cleanup removes only the rows this test wrote.
**Actual:** A real app tick landing at `t0` is deleted alongside the test row.

**Fix pathway:** Patch — insert test rows with a unique sub-millisecond offset strategy, or capture the inserted row's `id` and delete by `id` instead of `tickedAt`.

### [LOGIC-006] | Severity: LOW | `recentTicks` ordering depends on DB-side `ORDER BY` but is re-sliced client-side with no re-sort

`getCronTargetStatuses` collects events already ordered `desc(cronTickEventsTable.tickedAt)` from the DB, then iterates them into `eventsByTarget` per-target maps preserving insertion order (newest first). The `.slice(0, RECENT_TICKS_SHOWN)` on line ~236 is therefore correct — but only because the DB returns all events in a single query ordered globally. If two targets share nearly identical timestamps and the per-target grouping interleaves them, the target-level order is still preserved by the iteration sequence. However, `TickStrip` then does `[...t.recentTicks].reverse()` to get oldest-first, using the index `i` for gap calculation. If `recentTicks` is not strictly newest-first (e.g. future clock-skew rows were filtered mid-list by the `e.tickedAt.getTime() > now.getTime()` guard), the remaining array is not re-sorted before slicing, so gap calculations use incorrect ordering.

**File:** `artifacts/api-server/src/lib/cron-heartbeat.ts` — `getCronTargetStatuses()`, lines ~211–220; `artifacts/command-centre/src/pages/admin-ops.tsx` — `TickStrip`

**Expected:** `recentTicks` is always strictly newest-first after clock-skew filtering.
**Actual:** Filtering future rows mid-array leaves a gap in the sequence without re-sorting, so `TickStrip` gap-ms calculations may be wrong for adjacent entries around the filtered row.

**Fix pathway:** Patch — after the `for (const e of events)` loop that populates `eventsByTarget`, add `.sort((a, b) => b.getTime() - a.getTime())` on each target's list before slicing, ensuring the ordering invariant survives future-row filtering.

## Bug Triage Board

**1. [SYNTAX-001] — Zod `coerce.date()` vs. wire `string[]` type contract mismatch**
- **Severity:** HIGH
- **Blast Radius:** Every consumer of the generated Zod client that reads `recentTicks` — currently `TickStrip` and `TickHistoryLine`; any future consumer inherits a `Date[]`-typed field that is actually `Date[]` post-coercion but was intended as `string[]`, causing silent breakage if the consumer calls string methods.
- **Estimated Fix Time:** 15 minutes
- **Fix Pathway:** Patch — change `zod.coerce.date()` → `zod.string().datetime()` in `lib/api-zod/src/generated/api.ts` and update `cronTargetStatus.ts` to `recentTicks: string[]`.
- **Regression Risk:** Low — aligns three files to the wire format; existing UI code already treats values as strings (`new Date(iso)` still works on a string).
- **Why this matters:** The Zod validator silently coerces ISO strings to `Date` objects while the canonical TypeScript interface declares `string[]`. Any type-checked consumer downstream will pass type-checking against the wrong type, hiding runtime divergence until a string operation is applied to the coerced `Date`.

---

**2. [LOGIC-001] / [PFP-DRIFT-001] — Non-atomic insert-then-prune race condition in `recordCronTick`**
- **Severity:** HIGH
- **Blast Radius:** All four monitored cron targets; concurrent ticks (possible under Replit's multi-instance autoscale) silently lose tick events, causing `ticksLast24h` to under-count and the flakiness line to show false health.
- **Estimated Fix Time:** 30 minutes
- **Fix Pathway:** Patch — wrap the `db.insert` + `db.delete` pair in `db.transaction(async (tx) => { … })` using the transaction-scoped `tx` client throughout.
- **Regression Risk:** Low — transactions are already used elsewhere in the codebase; the prune logic is unchanged, only its isolation boundary moves.
- **Why this matters:** The entire value of the new `cron_tick_events` table is accurate tick counting. A race that silently drops tick rows undermines the one invariant the feature was built to provide, and the failure is invisible in logs.

---

**3. [LOGIC-002] — `notInArray` with empty subquery deletes all rows for the target**
- **Severity:** HIGH
- **Blast Radius:** Single target per invocation, but a misconfigured or edge-case `CRON_TICK_HISTORY_LIMIT` (e.g. 0, or a subquery that returns nothing due to a DB error) wipes the entire tick history for that target, leaving the flakiness line permanently blind.
- **Estimated Fix Time:** 20 minutes
- **Fix Pathway:** Patch — replace the `NOT IN (subquery)` pattern with a `DELETE … WHERE id IN (SELECT id … ORDER BY … OFFSET CRON_TICK_HISTORY_LIMIT)` pattern, which is safe-by-construction when the offset exceeds available rows; alternatively add a pre-flight row count guard before issuing the delete.
- **Regression Risk:** Low — functionally equivalent under normal conditions; removes a dangerous edge case.
- **Why this matters:** PostgreSQL's `NOT IN` semantics when the subquery is empty evaluate to TRUE for every row, making this a silent full-table wipe for the target — the worst possible outcome for a monitoring history table.

## What architect review MISSED

1. **[SYNTAX-001] — Zod coercion produces `Date[]` while the entire rest of the stack emits and consumes `string[]`.** The architect correctly updated the OpenAPI spec, React client type, and server type to use `string` — but the Zod validator was generated with `coerce.date()`, contradicting all three. This is a generator-output validation gap: the spec and the generated Zod schema diverged and no cross-check caught it.

2. **[LOGIC-002] — The `NOT IN (empty subquery)` total-wipe risk.** The pruning pattern was reviewed for its functional intent (keep newest N rows) but the degenerate case — where the `LIMIT N` subquery returns zero rows — was not stress-tested. This is a classic SQL `NOT IN` trap that static review consistently misses because the normal-path behaviour is correct.

3. **[LOGIC-006] — Clock-skew filtering breaks the newest-first ordering invariant before `recentTicks` is sliced and before `TickStrip` reverses it for gap calculation.** The future-row guard (`e.tickedAt.getTime() > now.getTime()`) was added correctly but leaves a hole in the sorted sequence without a post-filter re-sort, causing `TickStrip` gap-ms values to be wrong for any tick adjacent to a skipped future row.
