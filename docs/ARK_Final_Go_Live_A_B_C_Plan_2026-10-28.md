# ARK — Final Go-Live A/B/C Delivery Plan

**Date:** 28 October 2026  
**Product:** ATANDA Command Centre / ARK  
**Method:** SPARTAN scope and infrastructure compression; CODON module composition; CORDON dependency sequencing.  
**Status:** Proposed delivery contract, not an implementation or production certification.

## 1. Outcome and non-negotiable boundary

Give every existing F stage and customer-facing function a useful, bounded A-category service on the existing platform. Preserve the existing production floor, artifact lineage, mandatory governance, independent-verification labels and protected release gates. Keep unfinished infrastructure in B and scale-only capabilities in C, with explicit activation triggers.

The end user should always understand:

1. What this service can do now.
2. What artifact or result they will receive.
3. What inputs, entitlement and permissions it needs.
4. Whether the result is internally assessed, independently verified, delivered or actually operating.
5. How to correct it and return to the exact stage with a numbered new artifact.

**Active A is a service-level claim, not blanket activation of the original full specification.** A document preparation service cannot satisfy a protected publication gate. A hosting handoff cannot satisfy an automated deployment gate. A health checklist cannot satisfy live operational monitoring.

If a required safety control cannot operate, the affected protected action stays closed. Its bounded A companion can remain useful under a different, accurate service name. If no safe useful companion exists, the all-functions-A target is not achieved; report the exception rather than making the action appear active.

## 3. Infrastructure assumptions and limits

Use the existing managed application workflows, PostgreSQL, private object storage, Clerk/staff access, configured AI integrations, current email facilities and existing package/export mechanisms. Reuse existing session, artifact and review contracts. Do not replace the database, migrate authentication, add a second marketplace catalog or introduce Azure as a prerequisite for ordinary private work.

Latest public evidence from the preceding audit: application health 200, database available, AI configured, readiness 200, public SPHINX catalog closed. This is not provider availability, protected security installation, authenticated workflow acceptance or deployed-revision parity.

Development workflow availability must be checked at the start of execution; the latest environment notification reported stopped/failed web and API workflows. Do not confuse a development workflow failure with production outage.

Production role/security parity, provider authorizations, email delivery, scheduled services and billing configuration require fresh authorized checks. Read configuration presence without exposing values. Use integrations and supported secrets flows; no credentials in documents or test output.

## 10. Acceptance gates for an Active A service

Each of the 35 services needs evidence for:

1. **Discoverability:** correct place in the existing floor and accurate guide copy.
2. **Source and entitlement:** applicable owned input, role/tier and eligibility; missing prerequisites are explained rather than hidden as inactive development.
3. **Real outcome:** supported input produces an actual saved result or accurately reports a failure. No placeholder data.
4. **Inspection and portability:** editable/inspectable output and working download or meaningful persisted observation, as applicable.
5. **Persistence and recovery:** reload/re-entry, request retry, duplicate prevention and intelligible error recovery.
6. **Continuity:** exact-stage return and Upgraded N for supporting work; no automatic evidence inheritance.
7. **Security and truthfulness:** cross-owner rejection, private file handling, no secrets, authentic claims and no protected gate weakening.
8. **Usability:** desktop/mobile, light/dark, keyboard navigation, readable status/reason and a clear next action.
9. **Evaluation:** real applicable checks and negative tests; changed output receives fresh applicable assessment.
10. **Production evidence:** correct deployed revision and a minimal actual production smoke check using an authorized safe identity. No destructive fixtures or costly calls without approval.

One coherent browser acceptance pass per materially changed critical journey; use unit/API checks, logs and screenshots for cheaper confirmation where sufficient. Synthetic data must be identified; synthetic evidence cannot establish live provider acceptance or independent certification.

### Release blockers

- Any critical exploitable ownership/security defect or unsafe consequential write.
- Missing mandatory database protection on an action advertised as protected.
- Claimed delivery/deployment/certification without its real evidence.
- An advertised A flow that silently loses data, cannot retrieve output, or fails without recovery.
- No proven safe rollback/recovery path for consequential changes.
- Undisposed test failures affecting A behavior. The nine historical provider replay issues require a fresh status check and an explicit recording/cost decision; do not fabricate or re-key recordings. Acceptance must not silently ignore other genuine failures.

Paid tests, production writes, public opening and security administration require their appropriate explicit authority. The user performs publishing; the plan does not itself authorize a deployment or public marketplace opening.
