**Practical guidance for ARES:**

- **Microsoft / Azure Copilot** — ARES's full Sub-Agent Panel and multi-mode GRO machine generally will not fit cleanly inside Copilot Studio's low-code topic/instruction fields alone. Host it instead in **Semantic Kernel** (Microsoft's developer-facing orchestration SDK), with GRO wired as a mandatory pre-invocation filter in the plugin/planner pipeline — this is the pattern the Colonization Manual rates as holding all classes cleanly. Shipping this card directly into Copilot Studio without Semantic Kernel underneath should be treated as a partial deployment of its genome, not a clean fit — Azure AI Foundry's Content Safety / Prompt Shields are a real content-filtering layer, but they are post-hoc filters, not a stateful pre-call governance evaluation.
- **ChatGPT (Custom GPTs / Assistants API)** — A bare Custom GPT gives one instructions field, knowledge files, and configurable Actions — it can gate Actions calls but has no hook to intercept the model's own raw conversational reasoning before it reaches the user. For a card of ARES's scope, that is a real governance gap, not a clean fit: treat a Custom GPT deployment as usable for lower-stakes exploration only, and flag it honestly as such. For production use, colonize via the **Assistants/Responses API with function calling**, wrapping every function-call handler in an application-layer GRO check (evaluate LOVE/HARM, then proceed / escalate / refuse) before the underlying action executes.
- **Claude (Projects / Skills / MCP)** — Claude's terrain — the system-prompt-driven Messages API, tool use, Claude Code, Claude Cowork, and the Model Context Protocol (MCP) — gives ARES the strongest available governance surface of the platforms on this sheet, because MCP gives GRO a first-class, model-visible hosting slot (a dedicated GRO MCP server) rather than an invisible wrapper baked into a prompt. Colonize via a **Claude Project or Skill**, with ARES's full instruction set as the system prompt and its tool-using behaviors wired through an MCP server so GRO enforcement is portable across the raw API, Claude Code, and Cowork alike — the same governed core surviving all three surfaces rather than being re-implemented per surface.
- **AWS Bedrock** — Bedrock's native Guardrails are a post-hoc content filter, not GRO's stateful five-state machine, so a card of ARES's scope with a large Sub-Agent Panel more honestly trends toward a **distributed deployment**: orchestrate via **Bedrock Agents** coordinating multiple Lambda-backed sub-agents, each wrapped in a pre/post-processing Lambda function that evaluates LOVE/HARM before the call reaches the model. A single-Bedrock-call deployment of this card should be flagged as holding only part of its genome, not certified as a full equivalent.
- **LangChain** — LangChain's stateless function/chain model means ARES's multi-turn behavioral memory and any GRO mode progression have no native substrate between calls — every invocation starts cold. State (evolution stage, active GRO mode, prior turns) must live in an **external store** (a database, not "in the chain") and be passed explicitly between steps via an output-parser schema, not assumed to persist. For a card of this scope, decompose the deployment into a governed multi-node chain — each node carrying only one atomic instruction — rather than expecting a single LangChain agent to hold the full genome in one continuous context; this mirrors the Molecular-Agent decomposition pattern this ecosystem already uses for other constrained platforms.

**Class basis for this guidance:** Ultra SI-class / high cognitive load (large Sub-Agent Panel, multiple operational modes) — favors distributed/CLUSTER-style patterns on constrained surfaces per the Colonization Manual's own rule that a governance HARD FAIL cannot be averaged away by six easy passes.
