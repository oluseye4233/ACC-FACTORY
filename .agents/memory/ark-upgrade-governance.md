name: ARK upgrade governance
description: User-authorized upgrade program, live-status benchmark and safety boundaries.
---

The user wants the attached ARK/XVL/VTE/SHORT SPRINTS/IMPRIMA upgrades integrated
in dependency order without routine permission stops. Ask for unavailable
SPCs and pause only for fundamental missing inputs or consequential decisions.
Tell the user when a verified release is ready to republish; do not publish.

The user explicitly chose to retain Replit hosting and connect Azure Key
Vault. Do not migrate hosting/databases or silently replace that secrets
requirement with another provider.

**Why:** The user explicitly requested continuous integration work and progress
against the invariant register using active/inactive capabilities on the live
platform, rather than specification or development status alone.

**How to apply:** Keep source version, local build, published activity and
independent enforcement separate. Unverified is not inactive, and a passing
local test is not proof of live activation. Never invent missing SPC behavior,
legal approval or invariant text. Draft PDD policy conflicts and a requested
hosting/security-provider change need explicit resolution before enforcement.

The user subsequently authorized deriving replacement SP-17–SP-20 policies,
the sprint eligibility ruling and a current SEC REP ONE reassessment from
available specifications. New CODE DJ, ADA, CODON and CORDON STUB cards may
assist the engineering work; CODON and CORDON are distinct.

**Why:** The user explicitly requested gap-filling rather than waiting for
unavailable historical originals and gave implementation authorization.

**How to apply:** Label successor policy and authored adapter contracts as
derived; retain original missing-source provenance. Do not repeatedly block
on those same originals. New assessment results must be measured, not copied
from historical scores; implementation permission never fabricates legal,
external verification or authenticated waiver evidence.

Keep internal metadata auditing separate from training-corpus permission.
Artifact audit capture must not infer opt-in from artifact creation, Exemplar
sharing or Sphinx selection.

**Why:** Observing an engine output is not the owner's consent to train on or
export its contents; the upgrade PDDs require a distinct consent/ethics gate.

**How to apply:** Keep corpus eligibility closed until that gate is implemented
and verified. Do not count metadata traces as consented corpus records.

Verifier independence describes the test mechanism, not automatic product
conformity. A deterministic contract can be I2 while the stage still lacks
its required Blocking tracks, readiness signals and approvals.

**Why:** Owner-selected acceptance tests can be weak. Promoting a stage or
clearing SHORT SPRINTS/IMPRIMA from one passing contract would bypass the
source PDD's independent release requirements.

**How to apply:** Keep individual contract results separate from stage
conformity and existing certification/custody flags until the full profile
selection and gate evidence are implemented.

Pre-registration timestamps used as security fences must reflect database
wall-clock time after acquiring serialization locks, not transaction-start
time.

**Why:** A transaction can wait behind an artifact writer; transaction-start
time can make a later registration appear to precede the artifact.

**How to apply:** Use the same serialization boundary for temporal acceptance
contracts, and fail closed on ambiguous ordering rather than backdating.

For the launch MVP, apply SPARTAN to retain usable existing functionality and
defer unfinished upgrade activation rather than making every upgrade a launch
dependency. Keep mandatory safety, ownership and existing verification gates.
Azure remains the chosen eventual vault; MVP deferral is not cancellation.
The user explicitly authorized bypassing Azure requirements for now as a
**Class B follow-on build**. Azure credentials and rotation are not core MVP
launch gates; do not ask for them to continue core work. Keep existing secret
controls and fail-closed checks for genuinely vault-dependent operations.

**Why:** The user requested a SPARTAN MVP that launches and uses the database
and all usable features while upgrades proceed.

**How to apply:** Separate core launch requirements from future upgrade gates;
never interpret a frozen database as justification to replace it or fake data.

The final go-live scope requires a useful A-category service for every existing
F stage and customer-facing function on current infrastructure. Keep supporting
implementation/qualification in B and scale-only expansion in C, with explicit
triggers. Preserve original full-feature requirements beside each bounded A
service rather than treating preparation as independent approval or deployment.

**Why:** The user requested an all-stage functional launch using SPARTAN,
CODON and CORDON without waiting for infrastructure beyond present capabilities.

**How to apply:** Classify scope, compose validated existing modules and order by
real dependencies. Record local service acceptance separately from live
acceptance and original-contract completion; never mark missing authority,
security or evidence active simply to make the floor appear complete.
